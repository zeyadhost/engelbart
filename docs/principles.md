# Engelbart Engineering Principles

Engelbart is a compile-time USB device compiler for embedded C++. The first supported target is RP2040 / Raspberry Pi Pico WH using the Pico SDK and TinyUSB.

These principles guide the project before implementation begins and should be revisited when APIs, examples, and generated output change.

## Compile-time first

Engelbart should generate USB descriptors, HID report descriptors, endpoint layouts, interface numbering, and TinyUSB integration at compile time whenever practical.

Runtime work is acceptable for normal USB class behavior, data movement, and application logic. It is not the default place to construct descriptor trees, allocate endpoints, or decide interface layout.

## Deterministic descriptor output

The same device description, Engelbart version, compiler configuration, and target should produce the same descriptor bytes every time.

Determinism matters because USB hosts can be sensitive to descriptor details. Generated output must be stable enough to diff, test, review, and reason about.

## Generated bytes must be inspectable

Users must be able to see what Engelbart generated:

- USB device descriptors
- Configuration descriptors
- HID report descriptors
- Endpoint allocation
- Interface numbering
- TinyUSB glue

Abstractions are acceptable only if users can inspect the bytes and wiring below them.

## Zero-cost abstractions

Engelbart's higher-level C++ API must not require heap allocation, runtime descriptor synthesis, hidden registries, or unnecessary runtime dispatch for generated descriptors.

Convenience APIs are valuable, but the compiled output should be close to what a careful embedded developer would have written by hand.

## TinyUSB is an implementation detail

TinyUSB is the year-one USB stack and a critical implementation layer. Engelbart should generate TinyUSB-compatible descriptors and glue for RP2040 / Pico SDK projects.

The public model should describe USB devices, HID capabilities, descriptors, endpoints, and interfaces. It should not expose TinyUSB macros as the user's primary authoring model.

## Validation is a headline feature

Validation is not a secondary utility. Engelbart should explain invalid device descriptions as early as possible and in terms users can act on.

Examples of validation failures include endpoint budget exhaustion, illegal HID combinations, unsupported report shapes, duplicate interface assignments, invalid string policy, and target limits.

## Explicit escape hatches

Engelbart should provide clear ways to drop to lower levels when needed:

- inspect generated descriptors
- override selected defaults when supported
- use raw descriptor bytes in tightly documented cases
- integrate with TinyUSB directly for unsupported behavior

Escape hatches must be explicit. A user should know when they leave the validated Engelbart model.

## No hidden global magic

Device composition should not depend on hidden mutable global state, static registration order, constructor side effects, or runtime discovery of objects.

Implicit decisions such as endpoint assignment may exist, but they must be deterministic, inspectable, documented, and overridable where practical.

## No runtime descriptor synthesis by default

The core design rejects building a USB descriptor tree in RAM at runtime. Generated descriptors should be static data by default.

If runtime overlays are ever supported, they must be bounded, documented, and justified. Runtime identity string replacement is a different class of feature from runtime descriptor graph construction.

## Stable output is a compatibility concern

Descriptor byte changes can affect host behavior. Engelbart should treat generated output as compatibility-relevant even before 1.0.

When generated bytes change intentionally, the change should be documented, tested, and called out in release notes.

## Examples must not impersonate real USB products

Examples must not use real vendor IDs, product IDs, manufacturer names, or product strings in a way that impersonates real hardware.

Illustrative examples should use pid.codes-style test VID values such as `0x1209`, clearly fictional product names, and language that avoids spoofing or anti-cheat framing.
