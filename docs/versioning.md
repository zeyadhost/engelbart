# Engelbart Versioning

Engelbart starts as a pre-1.0 project. The API and generated output will change while the descriptor compiler, validation model, and inspection artifacts are designed.

## Pre-1.0 expectations

Before 1.0:

- Public APIs may break.
- Generated artifact formats may change and remain unstable unless explicitly marked stable.
- Descriptor output may change.
- Validation rules may become stricter.
- Public diagnostic IDs may change, but changes should be documented once IDs exist.
- The minimum inspection baseline is mandatory but not stable unless explicitly marked stable.
- Examples should track the supported public API.

Breaking changes should still be documented. Pre-1.0 does not mean silent churn is acceptable.

## Descriptor output compatibility

Generated byte output should be treated as compatibility-relevant.

When descriptor bytes change, release notes should explain whether the change is a bug fix, spec-correctness fix, host compatibility change, target constraint change, or intentional model change.

Golden tests should make output changes visible during review.

Report-ID support, if added later, must be explicit opt-in. It must not silently replace the initial no-report-ID mouse, keyboard, or composite HID descriptors.

## Diagnostic ID compatibility

Diagnostic IDs may change before 1.0, but once an ID appears in tests, examples, or public docs, changes should be documented.

After 1.0, public diagnostic IDs are compatibility-relevant. Tests should continue to assert IDs and key message fragments rather than complete compiler output.

## Post-1.0 expectations

After 1.0:

- Public API breaks require a major version.
- Generated byte changes require explicit documentation.
- Stable inspection artifacts should remain readable across compatible releases.
- Public diagnostic IDs should be treated as compatibility-relevant.
- Examples should continue to compile against the supported public API.
- Validation changes should avoid surprising users without release notes.

## ADRs

ADRs should record major design decisions, especially decisions affecting:

- project identity
- supported targets
- compile-time versus runtime behavior
- descriptor output stability
- public API shape
- validation policy
- inspection artifact formats

Unwritten decisions do not count as stable project policy.

## Examples

Examples should track the supported public API and remain honest about what exists.

Examples must not claim support for unimplemented features. They must not impersonate real USB products.

## Roadmap promises

Engelbart should not make public roadmap promises for unstaffed features.

Deferred features may be documented as deferred or exploratory, but the roadmap should avoid implying commitments to GUI, dashboard, Inspector, multi-board support, runtime reconfiguration, or additional USB classes before the core is proven.
