# Engelbart Testing Strategy

Engelbart's descriptor compiler should be tested from the beginning. Descriptor generation is mostly a pure transformation from typed device description to generated bytes, which makes it unusually testable for embedded software.

## Principles

- Treat descriptor generation as pure-function behavior.
- Prefer byte-exact tests for generated USB and HID descriptors.
- Test allocation decisions directly.
- Test validation failures as product behavior.
- Keep TinyUSB integration smoke tests separate from pure generation tests.
- Use CI from the beginning.

## Descriptor generation tests

Descriptor generation should be tested as pure-function output:

- input: typed device model and target
- output: descriptor bytes and allocation metadata

Tests should verify device descriptors, configuration descriptors, interface descriptors, endpoint descriptors, string descriptor policy, and any class-specific descriptors.

Descriptor generation tests must also verify descriptor byte emission invariants:

- every `bLength`
- configuration `wTotalLength`
- HID report descriptor length fields
- string descriptor `bLength`
- `bNumInterfaces`
- `bNumConfigurations`
- descriptor order defined by RFC 0002
- little-endian encoding of every multi-byte field

## Byte-exact golden tests

Golden tests should compare generated bytes exactly.

Generated descriptor bytes are compatibility-relevant, so byte changes should require deliberate review. Golden updates should include a reason, not just regenerated output.

Golden fixture updates should name the intentional behavior change, affected descriptor arrays, and any host-compatibility rationale. A golden update with no design reason should be treated as a test failure, not maintenance.

## HID report descriptor tests

HID report descriptor tests should cover:

- minimal mouse report descriptor
- minimal keyboard report descriptor
- composite mouse + keyboard report descriptors
- report size calculations
- absence of report IDs in the initial separate-interface composite model
- unsupported HID combinations
- HID report descriptor length fields in HID descriptors

## String descriptor tests

String descriptor tests should cover:

- fixed language ID descriptor `0x0409`
- manufacturer index `1`
- product index `2`
- omitted serial number index
- printable ASCII acceptance
- empty string rejection
- control character rejection
- non-ASCII input rejection
- UTF-16LE encoding with zero high byte for accepted ASCII
- string descriptor `bLength`
- maximum string length enforcement

## Endpoint allocation tests

Endpoint allocation tests should verify:

- deterministic endpoint ordering
- endpoint direction
- endpoint type
- endpoint packet size
- endpoint interval
- target endpoint limits
- exhaustion failures
- rejection of HID OUT endpoints in the year-one model

## Interface allocation tests

Interface allocation tests should verify:

- deterministic interface numbering
- composite device interface ordering
- interface count fields
- `bNumInterfaces`
- HID descriptor references to the correct interfaces
- failure cases for conflicting manual overrides, if supported

## Validation error tests

Validation errors are part of the user experience and should be tested.

Tests should cover invalid IDs, unsupported HID models, endpoint exhaustion, descriptor length mismatches, target incompatibility, missing required identity fields, and invalid override combinations.

Validation failures should expose stable diagnostic IDs once they are public. Tests should assert those IDs and key message fragments rather than complete compiler output.

Diagnostic ID tests should cover the initial taxonomy categories from ADR 0014: `STR`, `ID`, `ENDPOINT`, `INTERFACE`, `HID`, `DESC`, `TARGET`, `TINYUSB`, and `UNSUPPORTED`.

The test suite should avoid overfitting to one compiler's full diagnostic formatting, template backtrace shape, file path wording, or standard library wording.

## Compile-time failure tests

Compile-time failure tests should be used where practical.

The project should test that invalid C++ device descriptions fail compilation with expected diagnostic identifiers or message fragments. These tests may use CMake test projects, compiler invocation tests, or another focused harness.

Focused compile-failure test projects are appropriate for constraints that are meant to fail during template instantiation or `static_assert` evaluation.

Compile-time diagnostics are compiler-sensitive, so the strategy should avoid overfitting to one compiler's full error output.

## TinyUSB integration smoke tests

TinyUSB integration tests should verify that generated artifacts can be included in a Pico SDK / TinyUSB build for RP2040 / Pico WH.

Smoke tests should compile minimal mouse, keyboard, and composite examples. They do not need hardware for the first CI layer.

TinyUSB integration smoke tests should also verify descriptor callback routing:

- device descriptor callback returns the generated device descriptor
- configuration descriptor callback returns the generated configuration descriptor
- string descriptor callback maps indexes `0`, `1`, and `2`
- HID report descriptor callback maps HID instance `0` for standalone devices
- HID report descriptor callback maps mouse instance `0` and keyboard instance `1` for the composite device
- TinyUSB configuration values are consistent with generated HID instance count and endpoint packet size where detectable

## Host enumeration tests

Host enumeration tests are valuable but should be treated as later, manual, or CI-hardware-dependent.

These tests may eventually confirm that generated firmware enumerates on Linux, macOS, and Windows. They require hardware, host permissions, and careful flake control, so they should not block the initial pure generation test strategy.

## CI

CI should exist from the beginning and run:

- formatting or lint checks for documentation and source when available
- unit tests for descriptor generation
- byte-exact golden tests
- HID report descriptor tests
- endpoint allocation tests
- interface allocation tests
- validation error tests
- compile-time failure tests where practical
- Pico SDK / TinyUSB build smoke tests when the toolchain is available

CI should make unsupported hardware tests explicit rather than silently pretending that host enumeration is covered.
