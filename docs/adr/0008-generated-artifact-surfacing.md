# ADR 0008: Generated Artifact Surfacing

## Status

Accepted for Phase 1.5 architecture.

## Context

Engelbart must expose generated descriptors and TinyUSB glue without becoming a build-system replacement. The project targets Pico SDK, TinyUSB, CMake, and GCC ARM Embedded, but should not provide its own `build` or `flash` workflow.

The first implementation also needs an inspection story that supports tests and human review.

## Decision

The first implementation exposes generated descriptors as C++ compile-time/static artifacts.

Human-readable inspection dumps may be generated by tests or examples. JSON is deferred until the descriptor model and inspection needs are more stable.

CMake integration should be minimal and additive. Engelbart may provide target helpers or documented include patterns later, but it must not replace CMake, Pico SDK build logic, or flashing tools.

Engelbart will not provide `engelbart build` or `engelbart flash`.

Allowed CMake integration is limited to additive wiring such as include directories, source inclusion, compile definitions required by generated artifacts, or documented target helper functions. It must not own project configuration, build invocation, flashing, board selection outside the RP2040 / Pico WH target, or generated-artifact schema stability.

## Rationale

C++ static artifacts keep generated descriptors close to the embedded build and avoid introducing a separate generator binary or build phase before the model is proven.

Human-readable dumps are necessary for inspectability, but they can start as test/example output rather than a stable external artifact format.

Deferring JSON avoids locking in a machine-readable schema before the descriptor model, validation model, and inspection surface are stable.

Minimal CMake integration respects the existing Pico SDK workflow and keeps Engelbart focused on descriptor compilation.

## Tradeoffs

Generated headers or static C++ objects are less language-neutral than JSON or another external schema. That is acceptable for year one because the target audience is building embedded C++ firmware.

Text dumps may be useful but unstable before 1.0. Users should not be encouraged to build tooling around them until a format is explicitly marked stable.

Avoiding a CLI means there is no `engelbart inspect` command in the first implementation. Inspection must be available through generated/static artifacts, tests, examples, or build outputs.

## Consequences

- The descriptor engine should first produce C++ static artifacts consumable by Pico SDK / TinyUSB builds.
- Human-readable dumps can exist as non-stable test or example outputs.
- JSON inspection output is deferred.
- CMake support should be additive and documented, not a replacement build workflow.
- The roadmap remains free of CLI, dashboard, GUI, and host-side Inspector commitments.
